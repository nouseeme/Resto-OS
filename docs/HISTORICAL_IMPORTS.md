# Historical workbook imports

`server/legacy-import.js` parses and reconciles the legacy warung workbook. It reads only sales, debt reconciliation and expense records; it never imports HPP, margin, dashboard totals or unreferenced debt rows explicitly excluded by the import configuration.

`node scripts/plan-legacy-import.js config.json snapshot.json plan.json` creates a **preview only**. Configurations and database snapshots contain private customer data and belong in ignored `data/` directories. Each configuration supplies the exact source-file SHA-256, stable batch identifier, menu/customer aliases, approved payment corrections, excluded source rows, timezone and expected control totals. An unexpected file change, missing mapping, unreconciled balance or control-total mismatch stops the preview.

The snapshot has `{version, rows}` and contains the data tables from the cloud snapshot RPC. Authentication/session tables are unnecessary. Include prior `legacy_import` audit records to recognize an already completed batch. The original source workbook remains unchanged.

The planner preserves original prices, represents each portion separately, marks confirmed served portions delivered, links paid portions to payments, and closes fully paid historical transactions. All imported orders and payments must reference **new** historical transactions. A paid historical transaction may share a name with an existing live transaction, but it must not attach orders/payments to it. Unpaid imports colliding with an existing active name are rejected for manual reconciliation. The planner proves that existing records are unchanged and that no delete or update of an existing row is proposed.

Actual import uses the existing atomic `resto_commit` RPC, with guards checking that every proposed key is new and every imported order/payment references a new transaction. An outdated revision must abort the whole transaction; refresh the snapshot and rebuild the preview instead of overwriting concurrent changes. Keep the before snapshot and the applied changes as private import evidence. Afterward, compare every original row, reconcile control totals and verify individual corrected balances. Do not infer import success from the preview or an application build.

The batch has stable record IDs and an audit marker to prevent re-importing the same data. A partially present batch without its marker requires investigation and cannot be appended again. The imported payment dates use transaction dates as a historical date anchor; the file does not establish the actual settlement time. Metadata retains source file/hash, sheet/row/reference, date precision, timezone, import time and approved corrections. Never present midnight anchors as known event times.

This is an administrative, reviewed import path, not a public upload endpoint. New historical data does not pass through normal order creation, auto-accept, kitchen or repricing flows. Historical debt without item details requires a separate supported model or explicit exclusion; never fabricate menu items or revenue to represent it.
